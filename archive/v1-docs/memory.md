## ✅ RESOLVED 2026-09-27 — R0-1 violation in `neuroos-storage` (was 🔴 CRITICAL)

**What was actually wrong, confirmed by reading the vendored sources**: `lance-namespace` 12.0.0's `Cargo.toml` has an unconditional, non-optional dependency on `lance-namespace-reqwest-client` 0.12.0, which has an unconditional, non-optional dependency on `reqwest` (no `[features]` section existed in either crate). So the fix is: make `reqwest` an optional dep gated behind a new `client` feature (default off) in `lance-namespace-reqwest-client`, gate its `apis` module and `extern crate reqwest` the same way, then have `lance-namespace` depend on it with `default-features = false` and gate its own `apis` re-export the same way. Nothing that was actually reachable from `neuroos-storage`'s code paths lost functionality.

Five findings worth remembering, each of which cost real time:

1. **The pinned Kokoro model was four times too slow.** int8 synthesises at 0.9x real time — below real time, so a streamed answer can never catch up. fp16 turned out *larger* in memory than fp32 (the CPU provider expands fp16 weights and holds both copies). ADR-0016.
2. **C2 captured the real microphone whenever its configured node did not resolve.** PipeWire treats `target.object` as a preference, and `PW_KEY_NODE_DONT_RECONNECT` does not make it strict; separately, a sink's monitor is not a node at all. Found by refusing to accept a flaky integration test. For the one component that holds the microphone, this was the most important bug of the phase.
3. **whisper repeats itself on untrimmed audio with a shortened `audio_ctx`** — a 1.7 s clip came back as the same phrase eight times. Every captured utterance ends with FR-VOI-03's 600 ms of silence by construction, so trimming is a precondition for the latency optimisation, not an extra.
4. **Idle CPU was spent in a polling loop, not in the neural networks.** 1.73% of 2.45% was the main loop waking every 5 ms for frames arriving every 32 ms.
5. **An end-to-end smoke test found four defects unit tests could not**: two config keys missing from C2's own parser, a Landlock policy that denied PipeWire its configuration, the whisper repetition, and the CPU budget.

## 6. Decisions Log

**2026-10-12 (Phase 6 close-out, T5's verdict)**

- **ADR-0021 (Accepted, owner's D-32): C2's steady RSS budget raised 560 → 620 MiB**, taking PRD §6.2's total 2,630 → 2,690 MiB. **The reason is that the soak ran its full four hours for the first time.** ADR-0019 kept 560 MiB because `malloc_trim` brought steady RSS to 552 — but that came from a **12-minute** run of 35 turns, and the curve had not finished climbing. Over 4.00 h and **1043 turns**: idle 447 MiB, steady saturating at **602 MiB** after ~2 h and then flat at 597–602 for the final two hours and 543 turns, final reading below the peak, leak check **0.17%** against the 2% budget.
- **That it saturates is the finding, and it validates ADR-0019's mechanism.** glibc's dynamic mmap threshold ratchets upward only to a **32 MiB cap**; once every transient size C2 uses sits under that cap there is nothing left to migrate, so the retention is bounded where a leak would not be. `malloc_trim(0)` is therefore not a partial fix — it removes the unbounded component completely (the same harness read **1.87%** on the leak check without it, which over four hours is the failure mode that actually kills a service). What remains is a larger, finite working set.
- **The 768 MiB `MemoryMax` is confirmed, not raised.** VmHWM reached **680 MiB** over 1043 turns — 88 MiB of headroom, and the first evidence that C2 will not be OOM-killed in normal use. 0.7 xruns/h against a 600/h threshold. The EXIT trap left no stray daemon, no stray C5 and **0 null sinks** after four hours, so the `XDG_RUNTIME_DIR` fix holds under length.
- **A 55-minute reading of that same run said the opposite, and letting it finish is what corrected it.** At +55 min the trajectory read 551 → 566 → 588 with a projected leak check of **3.89%** and was reported as an unbounded climb. It extrapolated a ratchet still mid-climb — the same error as the 12-minute 552, in the other direction. **Caught before it reached a document**, which is the first of Phase 6's four budget-measurement errors of which that is true.
- **The lesson, now the fourth of this shape in Phase 6: a budget is evidence about the duration it was measured over.** `MemoryMax=520M` was below C2's idle floor; 640M was below its loaded peak; 560 MiB was below its *saturated* steady state. Each one passed every test that existed when it was chosen.
- **Pinning `glibc.malloc.mmap_threshold` was rejected a second time**, now against measured budgets on both sides: it fits 560 MiB comfortably (465–470 steady, 505–510 peak) but costs ~1 point of idle CPU on a real microphone, which breaches ADR-0020's fresh 3.5% FR-VOI-08 budget. ~42 MiB of the 602 MiB plateau is allocator retention rather than data C2 needs.
- **BUGS.md 8 (load-on-demand Kokoro) regains the value ADR-0019 took from it** and is now the largest remaining memory win in C2: ~350 MiB off *both* gates. Still deferred on scope — new behaviour in FR-VOI-05/10's paths.
- **`voice_pf.sh` verified after T4's restructuring** (it had been edited but not run): real device **2.300%** against the 3.5% budget, virtual **1.000%** against the 1.8% ceiling, RSS 447 MiB against 480 — all three green, measured at 4.0 GHz under load 0.81. The 3.00% worst case in ADR-0020 remains the budget's basis because it was taken in `powersave` at 2.1 GHz under heavier load.
- **The soak's own limitation, raised by the owner and recorded (BUGS.md 9).** The harness plays **one WAV 1043 times**, so every turn asks the allocator for the same transient sizes — the easiest case for the mmap ratchet to saturate in. "This is not a leak" is solid; "602 MiB is the plateau for *all* real use" is weaker, because varied utterance lengths size whisper's `audio_ctx` and Kokoro's activations differently and give the ratchet more distinct sizes to migrate. Bounded by the 32 MiB cap rather than open-ended, so the 620 MiB budget is not in question. **Follow-up:** drive the soak from a corpus of ~1–10 s utterances and re-run the four hours — a harness and fixture change, no shipped code.
- **"It was flat because the laptop was idle" is ruled out by the turn rate.** 259.8 turns/h in hour 0–1 and **259.8 turns/h in hour 3–4** — constant to within 0.2%, with 256 complete turns in the final hour while RSS moved 5 MiB. And an idle machine is the *pessimistic* direction for an RSS figure: a busy one creates memory pressure, the kernel reclaims, and RSS is pushed **down**. Load moves CPU clock and timing, not the number of bytes a turn asks for.
- **A short run of this harness cannot evidence the leak check, and the header used to claim otherwise.** A 0.20 h verification run read **2.14%** against the 2% budget and failed; the 0.12 h run read 1.87%. Neither is a leak — both catch the curve mid-climb, which is ADR-0021's own finding applied to the harness. `voice_soak_ms.sh` now asserts the leak check only at or above `min_hours_for_leak_check=2.0` (the measured saturation point) and below it prints `NOT ASSERTED` with the reason, and labels a short run's steady figure a **floor** (572 MiB at 0.20 h against the 602 MiB plateau) since a pass there is not evidence though a failure still is. **Not a §10.2.2 weakening:** the 4 h default, which is what the MS row asks for, asserts exactly as before; a duration that structurally cannot support the assertion now says so instead of failing falsely.
- **BUGS.md 8 re-valued upward**, reversing ADR-0019's cut: unloading Kokoro now removes ~350 MiB from **both** gates rather than the idle one alone, making it the largest single memory win left in C2.
- **Known doc drift, not fixed here:** design.md's healthd dashboard illustration (~line 274) still shows C2 at `381 / 405 MiB` and a 2,340 MiB total — it predates ADR-0014 *and* ADR-0017, so C2 is not the only stale row and patching one would make it inconsistent. Logged rather than half-fixed.

**2026-10-11 (Phase 6 close-out, T1–T5)**

- **ADR-0020 (Accepted, owner's D-31): FR-VOI-08 re-budgeted from < 1% to < 3.5% of one core, measured against a real microphone.** The important half is the measurement, not the number. Every idle-CPU figure in Phase 6 was taken against a null sink, which delivers *exactly* 0.0 — and C2's RMS pre-gate (`is_below_silence_floor`, floor 1e-4, in place since S01–S04 shipped) therefore skipped every frame, so Silero never ran. Real room noise is 0.0345 on this machine's internal mic and 0.00123 on its Bluetooth headset, 12–345× the floor, so on real hardware the gate is inert and Silero runs 31×/s as FR-VOI-02 intends: **2.30–3.00% of one core, localised by per-thread accounting to the detection loop** (the PipeWire thread is flat at 0.35–0.45% whatever the input). The pre-gate cannot be rescued by calibration here — measured acoustically, the room floor is 0.019–0.026 and speech at the mic 0.040–0.054, about **2× of separation**, and the test that would catch a false-reject regression is the KPI-4 real-voice corpus D-28 deferred. A cheap spectral first stage (band-energy or modulation rather than level) is the deferred answer.
- **ADR-0019 (Accepted, owner's D-30): C2's budget stays 560 MiB; only the ceiling moves, 640 → 768 MiB.** Written first as a raise to 650 MiB and **withdrawn the same day** once the mechanism was understood. The idle→steady climb was **not** whisper caching a buffer per `audio_ctx` size, as ADR-0017 and BUGS.md 0b both guessed: `whisper_init_state` reserves all four graph allocators and the KV caches at context creation, at the full `n_audio_ctx=1500` worst case, and C2 creates its context once at startup and only ever sizes `audio_ctx` *down*. It was **glibc's dynamic mmap threshold** — freeing a large mmap'd block raises the threshold (32 MiB cap), so the next one comes from the heap, and the heap only returns memory from the top, so a turn's large transients migrate in and stay. `malloc_trim(0)` once playback drains: idle 520 → **447 MiB**, steady 654 → **552 MiB**. The *peak* is live memory during a turn, so trimming barely moves it (670 MiB) and the ceiling still had to rise.
- **Pinning `glibc.malloc.mmap_threshold` was measured and rejected.** It is the bigger memory win (444 idle / 505 peak) but Silero's per-frame allocations then round-trip through mmap 31×/s, costing ~0.5 points of idle CPU on a silent source and ~1 point on a real mic.
- **The 54-leaked-null-sink mystery has a cause.** These harnesses `export XDG_RUNTIME_DIR="$run_dir"` to give the daemon an isolated socket tree, and `pactl` locates the session's PipeWire *through XDG_RUNTIME_DIR* — so every `pactl` call after that export, `unload-module` in the cleanup trap included, silently failed. Each run leaked its sinks. The three harnesses written last already had a `pactl()` wrapper pinning the real session runtime, which is why only they were clean; it is now in the five that lacked it.
- **A CPU-time percentage is not a reproducible budget without its conditions.** The same binary measured 0.85% and then 1.30% on the *virtual* source within one session — `powersave` at 2.1–2.6 GHz against a 3.2 GHz base, with a browser and a media player running. `voice_pf.sh` now prints governor, clock and load with every figure, and the virtual-source number is the control: when it moves, the machine moved.
- **Benchmarks must not pick the session default capture device.** A first pass read 3.4% on the "real device" while that device was a Bluetooth headset actively playing media; the same mic read 2.10% when idle. The harness now prefers a built-in `alsa_input.*`, with `NEUROOS_PF_CAPTURE_NODE` to override.
- **A `grep -c` that finds nothing prints 0 *and* exits 1**, so `$(grep -c … || echo 0)` yields `"0\n0"` — which made the soak's `[ "$turns" -lt 1 ]` a syntax error inside an `if` condition, where `set -e` does not catch it. The one guard that fails a soak of an idle daemon never fired.
- **Never edit a harness while it is running.** Bash reads a script incrementally, so a length change can misalign its read offset mid-run. A four-hour soak was restarted six minutes in rather than trust a measurement from a file that changed underneath it.

**2026-10-07 (Phase 6, S05–S08)**

- **ADR-0018 (Accepted): `BargeInNotice`/`BargeInAck`** on knowledge.sock (envelope 33/34, additive). A notification, not a request to stop -- C2 cancels C4 directly (inference.proto assigns `CancelRequest` to C2 and the ring header is the only place C2 can learn the generation id), and C5's read unwinds on the end-of-stream slot C4 writes on cancel. What the notice buys is that an abandoned answer is not recorded as a delivered one.
- **The turn runs on a worker thread.** Barge-in needs the VAD running while C2 speaks, and the detection loop used to sit inside the turn for the whole answer. The capture ring is single-consumer, so a second reader would steal frames -- the loop itself had to stop blocking.
- **Barge-in is armed from the playback stream's idle state**, not the turn's, so preambles and status clips are interruptible too. They are indistinguishable from the user's side.
- **A barge-in enters the follow-up window**, not idle: design.md §9.2 rule 5 is "stop instantly, *then answer the new question*", and the person who interrupted is mid-sentence.
- **The pre-roll runs during `kSpeaking` too**, so a barge-in captures the interrupting question from its start rather than from where the gate noticed it (~400 ms in). FR-PRV-04 is unchanged: bounded, in memory, never transcribed unless a turn opens.
- **`MemoryMax` 640M → 768M**, because the loaded peak is 696 MiB and systemd kills on the peak. A workaround, marked as one; the budget decision is the owner's (BUGS.md 0b).

**2026-10-07 (Phase 6, S01–S04)**

- **ADR-0016 (Accepted 2026-10-07): Kokoro re-pinned int8 → fp32.** Measured on this machine: int8 synthesises at 0.89–0.93x real time at every thread count (CPU dequantization costs more than the narrower arithmetic saves), fp16 at 4.2x but with 496 MiB resident because the CPU provider expands fp16 weights to fp32 and holds both, fp32 at 5.3x with 429 MiB. fp32 is both fastest and smallest in memory. `kokoro/tokenizer.json` added to the manifest in the same change — the phoneme vocabulary is the model's contract, so C2 reads it rather than carrying a transcribed copy.
- **ADR-0017 (Accepted 2026-10-07, the owner's call): C2's memory budget raised 405/520 → 560/640 MiB**, taking PRD §6.2's total from 2,475 to 2,630 MiB on a 15 GiB machine. PRD risk R-04 is closed as *materialised and funded*, not avoided: 82M parameters at 4 bytes is 328 MB of weights before any activation, and no quantization of this model is both smaller and fast enough to speak with. `MemoryMax` 520M was below C2's floor — the service could not start at all. **Load-on-demand Kokoro (idle ~100 MiB) is the better engineering answer and is deferred, not rejected** — preambles are already pre-rendered PCM and never touch the engine, so the cost is a ~1 s load before the first spoken *answer*, overlappable with C4's ~1.3 s prefill; what makes it a story rather than a config edit is that the clip cache must outlive the engine and FR-VOI-10 must tell "not loaded" from "failed". BUGS.md 8.
- **C5 gained a `VoiceCommand` handler on knowledge.sock**, sharing one `answer()` helper with `AskRequest` so the voice and `neuroosctl ask` paths cannot drift. C5 had no such arm, so C2's output had nowhere to go.
- **`VoiceCommand` gained `t_speech_start_ns` / `t_speech_end_ns`** (fields 3 and 4, additive). `spoken_at_ns` keeps its number and meaning. The deictic anchor must be when the user *started* speaking, not when the transcript arrived — those differ by a whole utterance plus transcription.
- **whisper's `audio_ctx` is sized to the utterance, on trimmed audio.** The trim is a precondition, not an optimisation: with trailing silence left in, a 1.7 s clip came back from audio_ctx 768 as the same phrase eight times.
- **A named PipeWire node is resolved to an id before connecting.** `target.object` is only a preference and falls back to the session default — measured, a capture stream pointed at a nonexistent node came up on the real microphone.
- **The capture ring drops oldest, the playback queue drops nothing.** Stale audio is worthless to a wake word detector; a dropped playback sample is a word the user does not hear.
